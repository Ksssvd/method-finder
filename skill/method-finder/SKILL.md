---
name: method-finder
description: 当用户贴出一个 AI 做出来的结果（或自己的作品）并表示不满意、觉得不对、说不上哪里不好、别人看了没反应时使用。适用于设计、动画、文章、PPT、文案、视频、产品方案、数据分析、决策、代码等任何任务。做法：先判断结果不好的根源（缺信息、缺标准、需求没想清、工具做不到），缺标准时找出最对症的、有公认名字的方法论（如 F 型阅读模式、迪士尼 12 动画原则、金字塔原理），然后直接按它重做出更好的结果，或给出改写好的提示词。触发说法包括"帮我找方法论 / 结果不满意 / 效果不好 / 总觉得不对 / 说不上哪里不好 / 怎么让 AI 做得更好 / 这种任务有什么方法论 / 帮我改提示词"；用户在开始一个任务前问"做这个有什么好方法"时也使用。只是纠正一个明确的事实错误或小改动（"把标题改成红色"）时不使用。
---

# 方法论匹配器

## 设计依据（先读懂，再执行）

1. **用户要的是更好的结果，方法论只是手段。** 所以能直接做出更好的结果，就不要只交一段提示词让用户自己再去跑一遍。
2. **结果不好有四种根源，方法论只能治其中一种。** 根源判断错了，推荐再好的方法论也没用。
3. **你本来就懂这些方法论，也本来就会分析问题。** 本 skill 要你做的，是你默认不会做的三件事：把根源分清楚；说出方法论的名字；让用户下次自己就会说。
4. **有没有变好，只有新旧对比才能证明。** 不对比就不能说"变好了"。

## 第 1 步：判断根源

看用户的任务、当前结果和他的不满（对话里没有结果就请用户贴出来），判断属于下面哪一种。可以同时有两种，但要说清哪个影响更大。

| 根源 | 怎么认出来 | 怎么办 |
|---|---|---|
| **缺信息** | AI 不知道给谁看、为了什么目的，或手里没有必需的数据和素材，只能写出放在哪都成立的通用内容 | 问用户补。最多 3 个问题，一条消息问完，每个问题给选项或示例答案 |
| **缺标准** | 信息是够的，但 AI 不知道这类东西"好"长什么样，结果平庸、杂乱、没重点 | 用方法论（第 2 步） |
| **需求没想清** | 用户自己也说不出想要什么，换什么版本都觉得不对 | 给 2–3 个差别明显的方向让他选，选定后再做 |
| **工具做不到** | 当前工具的能力限制，例如生图模型写不准文字 | 直说做不到，给替代办法，不硬套方法论 |

**缺信息时先问还是先做：** 缺的信息会改变整体方向（给谁看、目的是什么）就先问；只是缺具体数字或素材，就先做，缺的地方标【待补】，问题附在最后。

用户只说"感觉不对"时，不要追问抽象问题。自己看结果，列出 2–4 个具体症状让他选，例如："是 ① 看不出重点 ② 太挤 ③ 风格不统一 ④ 显得廉价？"能自己判断出来就直接判断，不用问。

## 第 2 步：选方法论（只在"缺标准"时）

1. 把不满翻译成**能指认的具体症状**，例如"不高级"→"字号层级少、留白不够、颜色超过 4 种"。
2. 按领域打开对照表，**只读需要的那一个文件**，按症状找：

| 领域 | 文件 |
|---|---|
| 界面、海报、网页、App 视觉设计 | `references/design.md` |
| 动画、动效、转场、角色设计 | `references/motion.md` |
| 文章、报告、邮件、说明文字 | `references/writing.md` |
| PPT、汇报、演讲 | `references/presentation.md` |
| 营销文案、标题、卖点、品牌 | `references/marketing.md` |
| 视频、分镜、故事、AI 生图生视频 | `references/video.md` |
| 产品方案、需求、PRD、功能优先级 | `references/product.md` |
| 数据分析、调研、竞品分析、找原因 | `references/analysis.md` |
| 做决定、做规划、定目标 | `references/decision.md` |
| 写代码、修 bug、技术方案 | `references/code.md` |
| 学习、讲解、教别人 | `references/learning.md` |
| 任何任务通用（结果不稳定、一次做不好、偏题等） | `references/general.md` |

3. **默认只选 1 个**最对症的。只有存在第二个不同的症状时才加第 2 个，最多 2 个。方法论越多，每个起的作用越小。
4. 只用真实、有公认名字、能搜到的方法论。表里没有的可以用自己的知识补，但拿不准名字或出处就不写，绝不编造。英文名只在确实有通用叫法时才加，没有就只写中文名。

## 第 3 步：行动

按任务在哪里执行，三选一：

- **当前对话里就能重做**（大纲、文案、文章、方案、分析等文字类结果）→ **直接重做**，不用先问。
- **重做会改动用户的文件，或者要花很长时间**（代码、设计稿、视频工程）→ 先说明打算怎么改，用户同意后再动手。
- **任务在别的工具里执行**（生图、生视频工具，别的 AI）→ 给一段改写好的提示词，放在代码块里方便复制。

**改写提示词的规则：最小改动。** 保留用户原来的提示词，只加针对症状的要求；每条新增要求都要能对应到一个症状；新增内容不超过 5 条。不加和症状无关的"保险"要求，要求越多，结果越臃肿。

重做时同样只改和症状有关的地方，用户没有不满的部分保持原样。

## 第 4 步：输出

按下面的顺序，除"新版结果"外，其余部分加起来控制在 300 字以内。全部用大白话，方法论第一次出现时用一句话解释。

```
**问题出在哪**
（1–3 句：属于哪种根源，具体症状是什么）

**用的方法：方法论名字（英文名，如有）**
（一句大白话解释它是什么；再用 2–3 条说明用在这个任务上具体意味着什么）

**新版结果**（或：**改写后的提示词**）
（重做的完整结果，或代码块里的提示词）

**和原来相比改了什么**
（2–4 条具体变化，只说事实，例如"结论从第 6 页挪到第 1 页"。
 给的是提示词时，这一段改成"预期会有什么变化"）

**还需要你补充**（没有就省略）
（缺的信息，最多 3 个问题）

**下次可以直接这样说**
（一句话，带上方法论的名字，例如："按金字塔原理重排，每页标题写成结论。"）
```

## 第 5 步：用户还是不满意

不要在同一个方法论上加码。回到第 1 步重新判断根源：多半是根源判断错了（例如以为是缺标准，其实是缺信息或需求没想清）。如果确实没有变好，直接承认，不要硬说变好了。

## 用户在任务开始前就来问

没有现成结果可以诊断。改为：先确认信息够不够（给谁看、目的、手里有什么），再预判这类任务最常见的 1–2 个失败点，各配一个方法论，直接按它开始做，或给一段"一开始就写对"的提示词。
