# 写代码、修 bug、技术方案

| 症状 | 方法论 | 一句话解释 | 写进提示词的具体指令 |
|---|---|---|---|
| bug 改来改去修不好 | 科学调试法（复现→假设→验证） | 先稳定复现，再提出假设，一次只验证一个 | 先写出稳定复现的步骤；列出可能原因并按可能性排序；每次只改一处并验证；没复现前不改代码 |
| 不知道问题出在哪一段 | 二分查找定位（如 git bisect） | 每次排除一半范围，快速缩小 | 用二分法定位：先确定好的版本和坏的版本，逐步对半缩小范围 |
| 找到了表面原因，问题还会再来 | 5 个为什么（5 Whys） | 追问到根本原因 | 修复后追问为什么会出现这个问题，直到找到根因，并修根因 |
| 代码越写越乱 | KISS / YAGNI / DRY | 保持简单；不写现在用不到的；不重复 | 只实现当前需求；不加预留扩展；重复三次以上的逻辑才抽出来 |
| 结构耦合、改一处坏一片 | SOLID 原则 | 面向对象设计的五条原则，核心是职责单一、依赖抽象 | 每个模块只负责一件事；模块之间通过清晰接口交互 |
| 功能做出来不对、反复返工 | 规格先行（Spec-First）+ 验收标准 | 先写清楚做什么、怎样算做完，再写代码 | 先输出需求规格和验收标准让我确认，确认后再写代码；完成后逐条对照验收 |
| 改动经常引入新 bug | 测试驱动开发（TDD） | 先写会失败的测试，再写代码让它通过 | 每个功能先写测试，再实现；每次改动后跑全部测试 |
| 大功能一次做不对 | 分而治之 + 小步提交 | 拆成小块，每块单独完成并验证 | 拆成可以独立验证的小步，每一步跑通后再做下一步 |
| 说不清问题是什么 | 小黄鸭调试法（Rubber Duck Debugging） | 一行行把代码讲出来，讲着讲着就发现问题 | 逐行解释这段代码预期做什么、实际做了什么 |
